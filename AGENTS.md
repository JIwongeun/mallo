# Repository rules

- This repository is the development source of the personal Relay orchestration plugin. Relay supports arbitrary local project folders, including this repository; do not require a parent hub, `workspace/`, or a secondary folder.
- Treat the task's primary working folder as the default target. Shared entry uses the installed plugin, not parent-repository inheritance or prior registration.
- Store project code, requirements, plans, run records, test evidence, and project-specific memory inside that project. Use `.codex-system/` for internal execution records.
- Keep immutable executable pipelines/defaults in the installed release and personal data outside the development checkout. The target reusable store is Knowledge under the user's data root. Generalize lessons and retain compact evidence snapshots; original project/run paths are optional provenance, never dependencies of admitted knowledge. Do not copy whole project data.
- Connect patterns through evidence-backed IDs and scoped relations. Similarity alone does not establish equivalence, contradiction, or a universal ban on a failed approach.
- Resolve the selected project path and Git root before running commands. Scope file edits, tests, and Git operations to that project. Respect its own instructions.
- Synthetic workspace fixtures and their trial knowledge were removed after provenance review. Future tests use temporary projects and isolated data roots. Preserve unexpected user data. Gitignore is not an access boundary.
- Use English for agent instructions, skill bodies, schemas, configuration comments, and generated machine-facing records. Human-facing guides and explanations may use Korean.
- Preserve original user requests, identifiers, code, quoted text, and error messages when fidelity matters. Do not translate evidence or rewrite existing project documentation without a task need.
- Keep documents compact: decisions, constraints, inputs, outputs, and necessary evidence only. Link to canonical information instead of duplicating it. Load details on demand.
- Keep the detailed implementation handoff in `docs/IMPLEMENTATION_PLAN.md` as requested, plus essential agent rules and a short README. Give other human-facing explanations in chat unless the user requests another destination. Do not write further Obsidian notes without a new request; Obsidian integration is outside the framework scope.
- Generation roles are Astra and Sol. Minimum effort is medium, normal work uses high, and complex work uses xhigh. Verify model availability on the execution host.
- Defer Jev and local embedding models beyond the first complete release. Do not add their clients, credentials, dependencies, or placeholder adapters now. Revisit only after an observed retrieval or efficiency need and a user decision.
- Establish acceptance criteria before execution. Distinguish review evidence, executed checks, user feedback, environment blocks, and changed requirements.
- Do not mark a pattern successful solely because a model says so. Revise only stages implicated by evidence, and preserve prior assessment revisions.
- Prefer native Codex capabilities, Node built-ins, and minimal dependencies. Do not add multi-user services or comparative benchmarks.
- Keep routing policy, execution state, Codex transport, and Knowledge storage separable. Use one execution controller, pin external skill revisions, and version persistent records.
- Self-development must execute from a fixed installed release while workers edit the source checkout. Freeze the legacy live-source launcher before executable refactoring. Pin release identity per run; promote only a verified committed artifact after active runs finish. Preserve a compatible rollback artifact and newer personal knowledge.
- Use reviewed local Git commits and immutable local release tags for versioning. Stage explicit paths and preserve unrelated changes. Do not push, publish, rewrite history, or change external plugins without a separate user request. Documentation-only work does not authorize starting implementation or creating a Goal.
- Discover available skills from current sources; the catalog is not a hardcoded roster. Recheck availability before dispatch, retain historical references after removal, and respect native hook trust when extensions change.
- The user manages external skill installation, updates and removal. Do not install, upgrade, edit or uninstall those skills/hooks as part of this framework implementation. Discover and select compatible installed skills; verify lifecycle changes with isolated test fixtures. This restriction does not exclude installing/updating this repository's own Codex System bridge.
- M0-M7 remain the completed legacy baseline. R0-R8 and their current evidence are recorded separately in `docs/IMPLEMENTATION_PLAN.md` and `.local/implementation-evidence/release-vnext.json`.
